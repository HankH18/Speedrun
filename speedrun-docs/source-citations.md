## Finding A — there is no minimum-review threshold constant (claim falsified)

The grep that was supposed to find the threshold returned **nothing relevant**. That is not a
tooling failure — the constant does not exist. The hits it did return
(`min_and_max_review_intervals`, `MINIMUM_EASE_FACTOR = 1.3`) are interval clamping in the
scheduler, unrelated to optimizer eligibility.

The authoritative statement is the doc comment on `compute_params` itself:

> `/// Note this does not return an error if there are less than 400 items -`
> `/// the caller should instead check the fsrs_items count in the return value.`

> ⚠️ **This finding was later corrected — read Finding G before relying on it.** The conclusion
> below is accurate for `rslib` and **wrong about the stack**: `compute_params` delegates fitting
> to the `fsrs` crate, which *does* gate, at 8 items. I searched Anki's Rust and stopped at the
> crate boundary. The scoped claim "no threshold constant exists in `rslib`" stands; the
> unscoped claim "Anki does not gate on review count" does not.

So **`rslib`** does not gate on a review count. It computes whatever it can and
returns `fsrs_items` alongside the params; deciding what to do with a small count is pushed to
the caller. The only early return in `compute_params` is for the genuinely empty case:

```rust
let fsrs_items = items.len() as u32;
if fsrs_items == 0 {
    return Ok(ComputeFsrsParamsResponse {
        params: current_params.to_vec(),
        fsrs_items,
        health_check_passed: None,
    });
}
```

**Any Brainlift claim of the form "if you have fewer than N reviews, Anki falls back to default
parameters, enforced by constant X" is not supported by this tree.** The fallback that does exist
is narrower: zero usable items returns the *current* params unchanged (not hardcoded defaults).

| [`6d13221a`](https://github.com/ankitects/anki/commit/6d13221ae50014e42338213d737e28b3af83d6df) | 2024-06-28 | [#3246](https://github.com/ankitects/anki/pull/3246) | **Removed** the gate from **`compute_minimum_recommended_retention`** (`retention.rs`) — a *different* feature from the parameter optimizer — replacing it with shrinkage toward a prior. |

The error variant and its localized string were left behind by both. Attributing the
*optimizer's* gate removal to PR #3246 is a misreading: #3246 never touched the optimizer.

**Stated rationale, quoted rather than paraphrased.** Issue #3094 (RlzHi), which drove the
optimizer-side removal:

> "We currently have a minimum of 1000 reviews for FSRS to be optimised, which I believe is now
> changing to 400. After some research and discussions with @L-M-Sherlock it seems we can lower
> this as far as 16, or remove it completely. […] The dry run is FSRS 4.5 without optimisations,
> and **after approximately 16 reviews optimising FSRS performs better than the default
> parameters.**"

The evidence cited is a fork of `srs-benchmark` (`notebook/metric_over_size.ipynb`) sweeping
metric against collection size over roughly 20,000 collections. In the same thread,
L-M-Sherlock raises a separate objection to counting raw reviews at all:

> "Assuming a new user does 1000 reviews in a deck of new cards, the `optimize` button still pop
> up the `insufficient data` error because those reviews are the first review of each cards. The
> first four parameters are pretrained in the second review of each card, and the rest params are
> trained in the third and following reviews of each card."

And Damien Elmes proposes the resolution that shipped:

> "Maybe one option would be to stop showing an error, and just fall back on the default
> parameters instead?"

PR #3246's rationale is different in kind and should not be conflated with the above. Its linked
issue ([fsrs-optimizer#116](https://github.com/open-spaced-repetition/fsrs-optimizer/issues/116),
Expertium) proposes replacing the hard cutoff with a weighted blend between the user's own
estimate and a default derived from 20k collections, weight `n / (50 + n)`:

> "The key idea is that when the number of times the user presses a button is very small, the
> estimate is not very accurate, and we should rely more on the default time, which we know is
> accurate. […] when a user has very few reviews, the simulation will rely mostly on the default
> values, and when the user has a lot of reviews, the simulation will rely mostly on his own
> review time values."

That shipped in June 2024 as `weight = total_first / (50.0 + total_first)` blending against
`DEFAULT_FIRST_RATING_PROB: [f64; 4] = [0.256, 0.084, 0.483, 0.177]` in `retention.rs`.

**Correction — this code is no longer in the tree, and an earlier draft of this file implied it
was.** `DEFAULT_FIRST_RATING_PROB` and the `n / (50 + n)` blend were deleted a month later in
[`52ce6e6a`](https://github.com/ankitects/anki/commit/52ce6e6a6b3372260add66b69037d02df4288304)
("Feat/FSRS-5", [PR #3298](https://github.com/ankitects/anki/pull/3298), 2024-07-21). At the
pinned commit `d735cd25`, `retention.rs` is 77 lines and delegates to
`fsrs::extract_simulator_config`; `first_rating_prob` now arrives from the caller's
`SimulatorConfig` rather than being estimated with shrinkage. A repo-wide search for
`DEFAULT_FIRST_RATING_PROB` returns only proto/plumbing references, and a search for any
`n / (50 + n)` form in `rslib/` returns **nothing**.

Three distinct things are easy to conflate here, and all three have been confused at some point
in this project:

| | What is shrunk | Where | Status at `d735cd25` |
|---|---|---|---|
| fsrs-optimizer#116 (proposal) | Median **review times** per button (seconds) | Upstream fsrs-optimizer | Proposal only; not Anki code |
| PR #3246 (shipped 2024-06) | **First-rating probabilities** `[0.256, 0.084, 0.483, 0.177]` | `retention.rs` | **Deleted** by PR #3298 |
| Speedrun's Memory score | **FSRS parameters** | Speedrun | Our own design; **no upstream precedent exists** |

Nothing upstream has ever shrunk FSRS parameters. Borrowing the `n / (50 + n)` *form* is
legitimate; citing it as precedent for shrinking parameters, or as live upstream code, is not.

**How this cuts.** #3106 is straightforwardly adverse to any high review-count threshold: the
benchmark says fitting beats defaults from ~16 reviews. #3246 is more nuanced — it *rejects the
hard-gate mechanism* while *affirming the epistemic premise*, that low-N estimates are
untrustworthy and must be pulled toward a known-good prior. Neither PR concluded that thin data
is fine. Both concluded that refusing outright is the wrong response to it.

## Finding C — the SQL approximation is INCORRECT

Resolving the helper to SQL terms. Column mapping is confirmed from `schema11.sql` and the row
readers in `rslib/src/storage/revlog/mod.rs` (`button_chosen: row.get(3)` → column `ease`;
`ease_factor: row.get(6)` → column `factor`). Note the trap: the SQL column named `ease` holds
the **button pressed**, and the ease factor lives in the column named `factor`.

```
has_rating_and_affects_scheduling()
  = has_rating() && !is_cramming()
  = (button_chosen > 0) && !(review_kind == Filtered(3) && ease_factor == 0)
```

In SQL that is:

```sql
-- correct
ease > 0 AND NOT (type = 3 AND factor = 0)
```

The approximation used was:

```sql
-- approximation as written
ease > 0 AND type NOT IN (4, 5)
```

Two discrepancies:

1. **It fails to exclude cramming — this is a real false-positive.** Anki excludes
   filtered-deck reviews taken with "reschedule cards based on my answers" disabled
   (`type = 3 AND factor = 0`). The approximation keeps them. Any collection that has used a
   filtered deck in preview mode will include rows Anki's optimizer discards.
2. **`type NOT IN (4,5)` is redundant, not wrong.** Manual (4) and Rescheduled (5) entries are
   written with `ease = 0` (see `rslib/src/storage/revlog/fix_props.sql:9,20` and the guard
   `where (ease between 1 and 4) or (ease = 0 and factor = 0)` at
   `rslib/src/storage/revlog/mod.rs:161`), so `ease > 0` already removes them. Harmless, but it
   conceals the actual exclusion rule.

Net effect: the approximation is **over-inclusive**, and the direction of the error matters —
it inflates the review count, which is exactly the quantity any "do I have enough data"
analysis depends on.

## Finding D — scope is per-preset, expressed as a search

`ComputeParamsRequest` carries `search: &'t str` plus `current_preset` / `total_presets`
counters. Optimization runs over the set of cards matched by a search string (in practice
`preset:"..."` built by the deck-options UI), not over a single deck and not globally. The
`current_preset`/`total_presets` fields exist only to drive the progress label
`deck-config-optimizing-preset = Optimizing preset { $current_count }/{ $total_count }...`
(`ftl/core/deck-config.ftl:487`) when optimizing all presets in a batch.

## Finding E — "graded reviews" is the wrong denominator; use `fsrs_items`

Anki does not train on reviews. It trains on `FSRSItem`s, and the mapping is not one-to-one.
From the construction loop in `reviews_for_fsrs`:

```rust
for (idx, (entry, &delta_t)) in entries.iter().zip(delta_ts.iter()).enumerate() {
    current_reviews.push(FSRSReview { rating: entry.button_chosen as u32, delta_t });
    if idx >= 1 && delta_t > 0 {
        items.push((entry.id, FSRSItem { reviews: current_reviews.clone() }));
    }
}
```

Three filters shrink the count, and all three are invisible if you count revlog rows:

1. **`idx >= 1`** — a card's *first* review never produces an item. A card reviewed once
   contributes zero.
2. **`delta_t > 0`** — the elapsed-days gap must be positive, so same-day repeats produce
   nothing. Drilling one card six times in an afternoon contributes at most one item.
3. **Cramming is dropped earlier**, at `params.rs:412`, before items are built at all.

So for a card with *k* qualifying reviews the yield is at most *k − 1* items, and the qualifying
condition is "card has ≥ 2 reviews on separate days." The worst case is not hypothetical — it is
the one L-M-Sherlock raises in issue #3094: a new user who does 1,000 reviews across 1,000 new
cards has 1,000 graded reviews and **zero** trainable items.

`compute_params` returns this count as `fsrs_items` in its response
([`params.rs:389`](https://github.com/ankitects/anki/blob/d735cd25d076051c6788b5a5acf65b57b9ea7277/rslib/src/scheduler/fsrs/params.rs#L389),
proto field `fsrs_items = 2`), which is precisely what its doc comment tells callers to inspect
in place of the gate it does not apply. **Any threshold this project sets should be denominated
in `fsrs_items`, not graded reviews.**

## Finding F — what the "~16 reviews" figure does and does not establish

Quoted accurately, and it is the basis on which Anki acted. But three qualifications belong
alongside it, none of which reverse it:

1. **It is a contributor's issue comment, not a published result.** The evidence is RlzHi's fork
   of `srs-benchmark` (`notebook/metric_over_size.ipynb`) with a plotted metric-vs-size sweep.
   Anki's maintainers found it sufficient to remove a gate; that is a real signal about their
   confidence, not a peer-reviewed finding.
2. **Its unit is "reviews", and the same thread argues that unit is misleading.** The 16 figure
   and L-M-Sherlock's objection that raw review counts overstate trainable data sit in the same
   discussion without being reconciled. Read against Finding E, "16 reviews" is plausibly closer
   to "16 items", which is a *stricter* requirement than it sounds.
3. **It compares fitted parameters against FSRS defaults — not against abstention.** It says
   fitting beats defaults from ~16; it says nothing about whether either beats refusing to
   report. That comparison is the one Speedrun still owes, and it is scheduled for
   `BRAINLIFT.md` Appendix B (assignment brief §10).

What it does establish is enough to be damaging to a high threshold: at the point where Anki's
own maintainers were willing to fit parameters, the data requirement was of order tens of
reviews, not hundreds.

## Finding G — low-data handling in FSRS-5+: the gate did not disappear, it moved down the stack

**This finding corrects Finding A, and the error was mine.** Finding A concluded "the backend does
not gate on a review count at all" and stated that a claim of the form *"below N reviews, Anki
falls back to default parameters, enforced by constant X"* is "not supported by this tree." That
was true of `rslib` and **false of the stack.** I searched Anki's Rust and stopped there.
`compute_params` delegates the actual fitting to the `fsrs` crate, and that is where the low-data
handling lives.

**Second pinned commit.** Anki's `Cargo.lock` pins `fsrs 6.6.1`. That version has **no git tag** in
`open-spaced-repetition/fsrs-rs`; the nearest tagged release is **v6.6.0**, SHA
[`56a78d97`](https://github.com/open-spaced-repetition/fsrs-rs/commit/56a78d971e73c16d2e9a757edfdc3d9e1f0b3695),
whose `Cargo.toml` reads `version = "6.6.0"`. **Everything below is read from v6.6.0, not from the
6.6.1 Anki actually builds against.** Differences between a patch release and its predecessor are
usually small, but this is an unverified gap and is labelled as such rather than papered over.

There is no single gate. There is a **graduated ladder**, and refusal sits at the bottom of it:

| `fsrs_items` | Behaviour | Where |
|---|---|---|
| **< 8** | **Does not fit at all.** Returns `DEFAULT_PARAMETERS` unchanged. | [`training.rs:319`](https://github.com/open-spaced-repetition/fsrs-rs/blob/56a78d971e73c16d2e9a757edfdc3d9e1f0b3695/src/training.rs#L319) |
| **8 – 63** | Fits only the four initial-stability parameters by ternary search; takes parameters 4–20 from `DEFAULT_PARAMETERS`. **No gradient training.** | [`training.rs:333`](https://github.com/open-spaced-repetition/fsrs-rs/blob/56a78d971e73c16d2e9a757edfdc3d9e1f0b3695/src/training.rs#L333) |
| **≥ 64** | Full gradient training, initialized from the above. | `training.rs:337+` |
| **> 300** | Only here does Anki run the FSRS **health check**. | [`params.rs:182`](https://github.com/ankitects/anki/blob/d735cd25d076051c6788b5a5acf65b57b9ea7277/rslib/src/scheduler/fsrs/params.rs#L182) |

```rust
// training.rs:319 — the gate that still exists
if train_set.len() < 8 {
    finish_progress();
    return Ok(DEFAULT_PARAMETERS.to_vec());
}
```

And **two genuine shrinkage-toward-prior mechanisms**, both inside parameter initialization:

```rust
// parameter_initialization.rs:118 — L1 penalty pulling initial stability toward the default
let l1 = (init_s0 - default_s0).abs() / 16.0;
logloss + l1
```

```rust
// parameter_initialization.rs:137 — Laplace smoothing of per-bucket recall
// (real_recall * n + average_recall * 1) / (n + 1)
(real_recall * count.clone() + average_recall as f64) / (count.clone() + 1.0)
```

The first is shrinkage expressed as a **penalty** rather than a weighted average: the further the
fitted initial stability strays from `R_S0_DEFAULT_ARRAY`, the more loss it pays, so thin data
cannot pull it far. The second pulls each recall bucket toward the collection's average recall
with a pseudo-count of 1. Parameters are additionally hard-clamped across all 21 slots in
[`parameter_clipper.rs`](https://github.com/open-spaced-repetition/fsrs-rs/blob/56a78d971e73c16d2e9a757edfdc3d9e1f0b3695/src/parameter_clipper.rs#L62).

Anki's own layer adds one more, which is neither a gate nor shrinkage:

```rust
// params.rs:156 — accept-only-if-better
if current_log_loss <= optimized_log_loss {
    params = current_params.to_vec();   // keep what you had
}
```

Fitted parameters are evaluated against the *existing* parameters on the same items and
**discarded if they do not improve log loss** — surfacing to the user as
`deck-config-fsrs-params-optimal` ("The FSRS parameters are currently optimal…"). This is exactly
what dae proposed in #3094 as the replacement for the error message, and it is a strictly better
instrument than a review-count gate: it tests the thing the gate was a proxy for.

**What this means for the give-up rule, stated plainly and against my own earlier reporting.** The
original BRAINLIFT claim — *"FSRS declines to fit custom parameters below a review threshold,
falling back to defaults rather than fitting noise"* — describes `training.rs:319` **accurately**.
The precedent exists. My correction overreached in saying it did not. What remains wrong about the
original claim is **magnitude and location**, and those still matter: the threshold is **8 items**,
not 200; it lives in `fsrs-rs`, not in the Anki codebase being forked; and it gates *fitting*, not
*reporting a score to a student*. A 200-item gate is **25× stricter** than the strictest thing
upstream does, and upstream's response to the 8–64 band is to shrink and clamp rather than to
refuse. Both facts point the same way: refusal is real precedent, but only at the extreme floor.
